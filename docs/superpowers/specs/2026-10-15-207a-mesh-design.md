# SP 800-207A incremental mesh design

The requested outcome is a runnable cloud-native extension of the existing 207 demo,
with a new branch and PR, without replacing its Passkey, device identity, PE/PA,
gateway PEP, Dashboard, or Compose topology. This implementation starts at main
`d629f859c24b471934c1517714fc676cdd618e42`; unrelated local Dashboard work stays separate.

## Decision and boundaries

Add an independent `mesh/` deployment in namespace `zta-207a`, running on a dedicated
kind cluster. Choose Istio sidecars (not ambient): the supplied 207A §1.2 explicitly
scopes the reference model to sidecar proxies. A separate frontend calls salary and
profile microservices, each with its own Kubernetes ServiceAccount. Istiod issues
SPIFFE URI workload certificates; STRICT PeerAuthentication and default-deny
AuthorizationPolicy enforce service identity, exact GET path, and destination port.
No LoadBalancer, NodePort, public ingress, host networking, or excluded application ports.

An in-mesh probe demonstrates authorized traffic; an injected intruder and a non-mesh
plaintext client demonstrate wrong-identity and unencrypted denials. Backend data is
synthetic. The frontend is an operator demonstration surface; port-forward is an
administrative tunnel and does not establish an authenticated end-user boundary.

Compared with migrating the entire 207 stack, an independent extension preserves
the existing demo and isolates workload identity from device identity. Compared with
two clusters immediately, one cluster permits meaningful negative-path validation
with much lower resource cost. Multi-cluster federation is deferred until trust,
east-west gateways, and actual cross-cluster denials can be tested.

## Optional external decision path

Keep the base mesh independently runnable. An optional overlay enables Istio CUSTOM
authorization using Envoy v3 gRPC CheckRequest. Its adapter uses the proxy-supplied
`attributes.source.principal` and `destination.principal`, never client identity headers.
It calls a new protected `/evaluate-service` endpoint in the existing PE application.
This endpoint uses a separate workload policy file and emits audit events through
the existing Context service. It does not turn SPIFFE IDs into device-a or fabricate
human tokens. Missing policy, PE, audit, or adapter must fail closed. Native ALLOW
policies continue to constrain CUSTOM decisions. No mesh policy is added to the
existing user/device trust score or PA session lifecycle.

## Acceptance

- Existing Python tests and original Compose/Envoy scenarios pass on this branch.
- Real sidecars and active SPIFFE certificates are inspected.
- Probe → frontend → salary/profile succeeds; intruder, POST, wrong path, direct Pod
  IP, spoofed headers, and plaintext attempts are denied.
- Optional ext_authz allows valid calls, observes policy revocation, and denies during
  adapter/PE/audit outages; restoration permits new valid requests.
- Versioned setup, verification, diagnosis, explicit cleanup, JSON evidence and CI
  are committed. No keys, tokens, kubeconfig, database, or PDF copies are committed.

## Standard mapping and limits

207 §3.1 supplies PE/PA/PEP separation. 207A §3.1 ID-SEG-REC-1/2/3 maps to encrypted
connections, workload credentials and granular service authorization; §3.3 and §4.6
require both network and identity tiers. Istio is the workload certificate issuer;
this is not a SPIRE deployment. NetworkPolicy requires an enforcing CNI and is not
claimed on kind's default CNI. 207A ID-SEG-REC-4/5 end-user identity at each hop is
not implemented by this service-only extension; the original Passkey demo remains
available separately. No claim of NIST certification, production HA, multi-cloud,
certificate federation, or complete standard compliance.
